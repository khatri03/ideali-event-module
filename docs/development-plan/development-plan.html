1. What this plans, and why now

The event module is mid-build: P6 adds coupons and refund UI, P7 adds organizer check-in. Before those screens land, the sidebar has two holes that will otherwise be filled ad-hoc and inconsistently. This document fixes both, and defines the home for the event reports the module can already back with real data. It is a plan, not code — it says what goes where and why, so a second agent builds with no guessing.

The two gaps

Gap 1 — reports have no home. The route /analytics exists but is a dead placeholder that renders <Settings /> (App.tsx). The sidebar item labelled "Custom Reports" points at /organizer/custom-form-report — that is the membership form-report builder, a different domain. Any new item just called "Reports" would collide with it in the user's head.

Gap 2 — check-in is an orphan. The screen EventCheckInPage is already routed at /organizer/events/:eventUniqueId/sessions/:sessionUniqueId/check-in, but nothing in the UI links to it. Door staff cannot reach it.

Reports only earn a place when they map to data the module already holds and a decision someone makes with money. No vanity dashboards. Every report below passes that bar; three candidates that fail it are named in §4 so nobody rebuilds them.

Reports are organizer-wide, not event-only — build them that way now. Exhibition and Trips modules are coming. Four of the six reports (Unpaid, Sales, Refunds, Coupons) are pure money questions with the same shape across every module — module is a where clause, not a new screen.

So the reports namespace, the route group, the feature folder and the sidebar group are all scoped to the organizer, not to events. Nesting them under /organizer/events/... would force a full triplication (a second Reports fold under exhibitions, a third under trips) or a painful route retrofit — bookmarks and muscle memory break, the exact confusion this plan exists to kill. Nav is the one thing costly to move later. Get the namespace right on the first pour. See §2.

2. Navigation decisions

Three decisions are settled. Treat them as fixed, not open questions.

DecisionResolution
Reports One collapsible sidebar group named "Reports", styled exactly like the existing Settings / Admin / Member collapsible sections. Six child links — one per report type (not per module). Each report takes a module filter (Event / Exhibition / Trip / All). Not six flat items, not a reuse of the "Custom Reports" label, not a fold-per-module.
Check-in Contextual entry only. No sidebar item. Reached by buttons from the Session row, the Event detail, and the Attendance report.
Refund & coupon (P6) Refund is an action on the invoice detail page, not a nav item. Coupon usage is one of the six report child links, not its own nav item.

Net new sidebar entries: one collapsible group. Everything else is reached from context it already belongs to.

Before / after the sidebar

Proposed layout, not a shipped screen. The Reports group sits first among the collapsible sections — above Settings — because organizers hit it often (unpaid, sales checked daily), while Settings is configure-once. Order by traffic, not by importance. One cost to accept: the busiest report now sits behind a fold; if daily friction shows, promote the top report (Unpaid or Sales) to a flat mainNav shortcut and keep the rest folded.

3. The "Reports" group — exact spec

Copy the pattern that already exists; invent nothing new.

  • Model on SettingsSection in src/components/layout/Sidebar.tsx (lines 185–316): same header button, same ChevronDown/ChevronRight toggle, same auto-open when a child route is active.
  • Header icon: BarChart3 from lucide-react, size={17} to match every other section header.
  • Gating: visible to Organizer + Admin — reuse the hasOrganizerAccess predicate that already guards SettingsSection.
  • Insertion point: in the ordered Box (Sidebar.tsx lines 650–678), render ReportsSection first among the collapsible sections, immediately before SettingsSection.
  • Open state: add an isReportsOpen flag mirroring isSettingsOpen, auto-opened when the path starts with /organizer/reports.
Do not relabel or repurpose the existing "Custom Reports" item — it is the membership custom-form-report builder and must stay where it is. Two "report" concepts in one sidebar will be mis-clicked no matter how the routes separate them, so rename hard, not just re-route: the new group is plain "Reports", and if both are visible to the same role, retitle the old one to "Form Reports" (or similar) so the label alone tells them apart. Labels do the disambiguation; routes only enforce it.

Routes & where to wire them

One organizer-scoped namespace, /organizer/reports/* — not under events, so Exhibition and Trips reuse the same routes with a module filter. Add a reports group to src/utils/routes.ts, and register the pages inside AppLayout in src/App.tsx, lazy-loaded with a skeleton fallback (the repo's established page pattern).

// src/utils/routes.ts — new group (organizer-scoped, module is a filter, not a segment)
reports: {
  base:        "/organizer/reports",
  unpaid:      "/organizer/reports/unpaid",
  sales:       "/organizer/reports/sales",
  attendance:  "/organizer/reports/attendance",
  refunds:     "/organizer/reports/refunds",
  sellThrough: "/organizer/reports/sell-through",
  coupons:     "/organizer/reports/coupons",
},
// module (event | exhibition | trip | all) travels as a query param on each report,
// e.g. /organizer/reports/unpaid?module=event — never a new route per module.
Every report list is server-paged, sorted and filtered in the same request, and takes its total from the server — same rule the Event Invoices list already follows. No fetching a whole collection and slicing in React.

4. The six reports

Each is ordered by build priority. Priority = the money decision it unblocks soonest against data already shaped. Reports 1, 2, 4, 6 are pure money — identical shape across Event, Exhibition and Trip; module is a filter. Reports 3 and 5 diverge per module (attendance = participants/visitors; capacity = seats/booths/slots) — one report each, module-aware view inside, still no separate route.

1 · Unpaid Invoices Priority 1

Pending invoices, aged, amount owed, buyer contact — sorted oldest first.

Reads: invoice status + createdAt aging. Decision it drives: who to chase for cash today. Every unpaid invoice is money on the table. Endpoint (unverified): GET /api/reports/unpaid?module=.

2 · Sales & Revenue Priority 2

Per event: gross sold, net after refunds, platform take-rate cut, broken down by session and ticket type.

Reads: invoice line totals + refunds + take-rate. Decision it drives: the settlement number — what the event made and what the platform's cut is, reconciled against Stripe payout. Endpoint (unverified): GET /api/reports/sales?module=.

3 · Attendance Priority 3 module-aware

Per session: issued vs checked-in, no-show rate, check-in time distribution. Hosts the "Live check-in" entry button (see §5). Label shifts per module — "attendees" for an event, "participants" for a Trip, "visitors" for an Exhibition — same columns underneath.

Reads: ticket ticketStatus + checkedInAtUtc (already on the invoice line items). Decision it drives: next-event capacity and overbooking; live "how many in the room". Endpoint (unverified): GET /api/reports/attendance?module=.

4 · Refunds & Cancellations Priority 4

Every refund/cancel: who, when, amount, reason, which invoice. Rides with the P6 refund UI.

Reads: cancelled invoices + refund records + actor. Decision it drives: reconciliation and dispute defence; refund rate as a health signal (it eats the take-rate). Endpoint (unverified): GET /api/reports/refunds?module=.

5 · Sell-through Priority 5 module-aware

Per session + ticket type: capacity, sold, held, available, % sold, sold-out time. Capacity unit shifts per module — seats for an event, booths for an Exhibition, slots for a Trip — same "% sold / available" math on top.

Reads: ticket types + line items + Seats.io capacity/holds. Decision it drives: repricing and whether to open more seats — "VIP sold out day one, GA 40% unsold". Endpoint (unverified): GET /api/reports/sell-through?module=.

6 · Coupon Usage Priority 6 · P6

Redemptions per code, discount given, revenue with vs without.

Reads: coupon redemptions (partial until P6 lands). Decision it drives: promo ROI — kill a code that gave away discount for no extra sales. Endpoint (unverified): GET /api/reports/coupons?module=.

Deliberately NOT built

  • Buyer demographics / cohort dashboards — no demographic fields captured. Charting nothing. Would need a new collection first.
  • Predictive / forecast reports — no historical volume yet (pre-production). A forecast on zero history is noise.
  • Real-time streaming dashboard — over-built. On-demand refresh (refetchOnMount: "always", already used on invoices) is enough; no WebSocket infra for a screen nobody keeps open all day.

5. Check-in entry points

The screen exists. It needs doors into it, not a sidebar item.

FromAction → target

Event detail (per session)"Check-in" button on each session

No sidebar item, on purpose. Check-in needs both event and session context; a global link would dead-end on a picker with nothing chosen. Current roles are only Organizer and Admin — there is no door-staff persona yet to justify a top-level entry. Reach it from the session it belongs to. Revisit only if a door-staff role is added.

6. Where P6 & P7 land

  • P6 — Refund UI. An action on the invoice detail page. Extend src/features/event-invoices/components/EventInvoiceSettlementActions.tsx. It is a privileged, audit-logged action — confirm with the consequence named, show pending and result states. No new feature folder, no nav item.
  • P6 — Coupons. Authoring already lives in the event wizard (discount-coupon step). The only new surface is the Coupon Usage report (report #6). Nothing else.
  • P7 — Check-in. Screen already routed; this plan only wires its three entry buttons (§5) and surfaces its outcome in the Attendance report (#3).

7. The backend blind spot

Every report needs a server-side aggregation endpoint in ideali.api. Before building any report screen, confirm its endpoint exists. The six endpoints in §4 are listed as unverified on purpose — none is assumed to be live.

If an endpoint is missing, that is backend work first. Do not hand-roll aggregation in React by pulling whole collections and summing them — that violates the server-side paging/aggregation rule and will not survive real data volume. A report fed by client-side math is a report that lies the moment the data outgrows one page.

Same bar as every shipped screen.

9. Build order

  1. Confirm the backend aggregation endpoints exist (§7) before any screen — this is step 0, not an afterthought. A missing endpoint is backend work first; no client-side summing.
  2. Sidebar group + routes shell. ReportsSection, the organizer reports routes, and six lazy pages rendering an empty-state skeleton. Nav is correct before any data lands.
  3. Report 1 — Unpaid Invoices. Cash recovery, simplest aggregation, confirms the endpoint-first flow end to end.
  4. Report 2 — Sales & Revenue, then 3 — Attendance (wires the check-in "Live check-in" button and the other two entry points).
  5. Reports 4 — Refunds (with P6 refund UI on invoice detail) and 5 — Sell-through.
  6. Report 6 — Coupon Usage, once P6 coupon data is flowing.

Each step confirms its backend endpoint before the screen is built (§7), and lands with its own tests. Nothing is reported done while a suite is red.
