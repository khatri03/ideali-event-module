1. What this covers

Everything the backend does between a visitor opening an event page and an attendee being scanned in at the door. Every endpoint involved, the service method behind each one, how the cart holds seats, exactly how each payment method's total is built, and what runs on its own afterwards.

Before deploying this module anywhere, including a laptop: EventCartCapability:SigningKey must be set or the API will not start. Before writing a frontend that talks to it: the axios client needs withCredentials: true or every cart call after creation returns 403.

Both come from the same feature — carts are anonymous and are guarded by a signed cookie instead of a login. Who is allowed to touch a cart explains why, with the failure modes for each.

Who this is for

Backend developers working on the Event module, and frontend developers who need to know what the server will and will not do for them. No prior knowledge of the codebase is assumed — every term is defined in section 2 before it is used.

The shape of it, in six sentences

  1. A visitor opens an event page; the server returns the event and which steps this particular event has.
  2. They create a cart — which is really an unpaid invoice — and add lines to it, each line taking a real hold on seats.
  3. If the organizer asked for them, the buyer names each attendee and answers the questionnaire.
  4. The cart is priced, producing a different total for each payment method.
  5. They pay; Stripe confirms it to the server through a webhook, which is the only thing the server trusts.
  6. Tickets are issued and emailed by background jobs — no browser required.
Two rules underpin everything below. The server prices the cart; a total supplied by the browser is never trusted. And the Stripe webhook — not the buyer's redirect — is the authority on whether money arrived.

2. The pieces involved

Every term used later, defined once. Skim it now and come back when a name is unfamiliar.

What the organizer sets up first

Organizer
The customer organisation running the event. Everything belongs to one.
Event
What is advertised. Owns the branding, the terms, the custom forms and questions, the payment methods and the charge rules.
Session
A dated occurrence of the event. Tickets are sold against a session, not the event, because an event may run over several days. Carries the RequiresAttendeeInfo flag.
Ticket type
A sellable class of seat inside a session — "Early bird", "Student". Holds the full price, the capacity, the per-order quantity limits and the sale window.
Ticket price period
A dated price for a ticket type, so the price can change on a schedule without editing the ticket type itself.
Payment account
The organizer's connected Stripe account and currency. Which methods are offered comes from the event's own EventPaymentMethod rows.
Charge rule
An extra fee the organizer adds — a booking fee, a service charge. Defined once as an OrganizerChargeRule and switched on per event as an EventChargeRule.
Revenue plan
What the platform charges. Its rules say whether the buyer or the organizer pays. Assigned to an organizer per module.
Processor fee
What the organizer adds to cover the payment gateway's own cut. Configured per payment method, which is why totals differ between methods.
Discount coupon
A code the buyer can enter. Validated at pricing time and only actually spent when the order settles.

What the buyer's journey creates

Cart
Not its own table. A cart is an Invoice with status PendingPayment. Its uniqueId is the buyer's only handle on it.
Cart line
Three rows together: an InvoiceItem for the money, an EventInvoiceItem for what was bought, and a TicketReservation for the actual seat hold.
Reservation
The stock hold. Active until it is confirmed, cancelled or expires. Everything that counts availability counts these.
Attendee
An EventInvoiceItemAttendee, one per seat, submitted before payment. Becomes the named holder of a ticket at issuance.
Submission
The questionnaire answers for the whole order — one EventPurchaseSubmission, regardless of how many tickets.
Charge snapshot
A PaymentChargeSnapshot recording why a charge was made — the rule, its value, its label, the currency — frozen at that moment so later edits never rewrite history.
Payment attempt
An InvoicePayment. Its ReferenceNo is the Stripe payment intent id, which is how settlement finds the invoice again.
Ticket
An EventTicket, created only once payment is settled. Carries the code scanned at the door.
The single most useful thing to internalise: a cart is an invoice, and a seat hold is a reservation. Almost every question about registration resolves once those two are clear.

3. The journey at a glance

Steps 4 and 5 appear only when the organizer configured them. Step 8 is the authority on payment; step 7 only starts it. Steps 9 and 10 need no browser at all — close the tab after paying and the tickets still arrive.

GET /api/organizer/events/{e}/sessions/{s}/attendees EventAttendeeRosterService.GetRosterAsync The door list: everyone holding a live ticket for that session, with arrival state, plus session-wide counts that ignore the search term. Searchable by name, email, ticket code or invoice number — the fallback when a code will not scan. Cancelled and refunded tickets are left off. Each row carries outstandingAmount, read live off Invoice.BalanceAmount and null once the order is settled, with outstandingCurrency on the roster itself because the currency belongs to the event rather than to any one ticket. It is on the row and not only on the scan reply because a guest who reads out an invoice number is admitted from this list without a ticket ever being scanned — without it the operator commits before they can ask for the money.
POST /api/organizer/events/{e}/sessions/{s}/check-in TicketingService.CheckInAsync Scans a ticket code at the door and writes a TicketCheckInLog row. Event and session come from the route, so a scan can only ever land on the session the operator opened. Refuses a code that is already used, cancelled or refunded. The reply carries attendeeName alongside the code, so the door can name the person it just admitted without going back to the roster. It also carries outstandingAmount and outstandingCurrency, read live off Invoice.BalanceAmount and null when the order is settled — an organizer may issue a ticket against an unpaid order (a cheque taken but not banked is the everyday case), and the operator collecting that money never sees the buyer's invoice. Whether it is a notice or a gate is the organizer's own decision, taken once on the event's advanced-settings step: with Event.BlockEntryUntilPaid off the balance never blocks admission and the operator decides, and with it on a ticket whose order still owes money is refused with PaymentRequired — logged apart from Invalid and OutsideWindow, so the audit trail says how many were turned away over money rather than over a bad ticket. The refusal still carries the amount, because the guest is being sent to a cashier who would otherwise have to go looking for the invoice. Someone already inside is left inside: a second scan still answers AlreadyCheckedIn whatever is owed, since turning it into a refusal would leave the roster disagreeing with the room. It is the event's policy and not the session's because who may enter unpaid is one answer for the whole event, unlike the door window, which is per session. There is no desk-side override: the organizer sets the policy, and the desk cannot wave it through. Both this policy and Event.ApplyPaymentMethodCharges are carried on the wizard's review summary and shown there in words, because the review step is the last place either is seen before publishing and neither is recoverable afterwards without stranding someone: the fee choice moves money off every payout, and the door policy turns guests away on the night. The balance repeats on an AlreadyCheckedIn scan because the operator reading it may not be the one who opened the door. A scan is also refused outside the session's own door window — from Session.CheckInOpensBeforeMinutes before Session.StartDate to Session.CheckInClosesAfterMinutes after Session.EndDate, falling back to two hours and three hours when the session declares neither — and that refusal is logged as OutsideWindow rather than Invalid, so the audit trail separates a bad ticket from a bad time. The window belongs to the session and not the event because attendance varies by an order of magnitude between them: a thousand-seat hall has to start admitting long before a hundred-seat room does. Both values are minutes, bounded to 0–10080, and are set on the session wizard's e-ticketing step, which offers the round windows an organizer actually picks (15 minutes through a day) and keeps a custom field for the rest, so the common case cannot be mistyped. Without it a leaked code could be burned weeks early and the real holder met with AlreadyCheckedIn on the night. A session that declared no dates is left open rather than shut. The undo path carries no window: a mistaken admission is discovered at any hour. The window itself lives in SessionCheckInWindow rather than in this service, because EventAttendeeRosterService needs the same two instants to tell the door screen how long is left. Working them out in two places is how a countdown reaches zero on a door that the next scan still refuses.
POST /api/organizer/events/{e}/sessions/{s}/check-in/undo TicketingService.UndoCheckInAsync Reverses a mistaken admission: the ticket returns to Active and the reversal is appended to the log as ManualOverride. The original admission is never erased. The reply carries attendeeName too, so the operator can see who was turned back.
EventTicketSalesController — POST /api/events/tickets/reservations, /checkout/invoice and /checkout/confirm — is the earlier, single-line purchase path that predates the cart. It still compiles and still works, but new work belongs on the cart endpoints above. Do not mix the two in one journey. GET /api/events/{id}/register/payment is superseded the same way: it takes a subtotal from the caller, whereas POST /cart/{id}/price derives it from the server-owned cart. Never trust a total the browser supplies.

5. How the cart actually works

The cart now lives in the event module before money exists. An EventInvoice is the cart, EventInvoiceItem rows are the lines, and TicketReservation rows remember what the buyer selected. A shared Invoice is raised only when checkout starts, because an abandoned cart is not an order. The important rows are:

Why EventInvoice comes before Invoice

The shared Invoice table is used by Donation and Membership too, so the cart no longer writes there while a buyer is only browsing. RaiseInvoiceAsync creates the shared invoice at payment start, links it back to the EventInvoice, mirrors live cart lines to InvoiceItem, and marks the cart Converted.

The hold clock

How longEvent.PurchaseTimeLimit if the organizer set one, otherwise AppSettings.PurchaseTimeLimitMinutes, otherwise a built-in default. Resolved by TicketingShared.GetEffectiveHoldMinutes.
Counted fromThe cart's creation time, not the line's. Every line shares one deadline, so adding a line late does not extend an already-aging cart.
Who enforces itEventCartMaintenanceHostedService, every minute. It marks expired open carts Abandoned. TicketingService.ExpireStaleReservationsAsync owns reservation expiry and counter refresh, so the two background passes do not fight over stock.
What the buyer seesexpiresAtUtc on the cart response. Once it passes, pricing refuses the line with "the hold has expired; remove and re-add this line".

Who is allowed to touch a cart

A cart is anonymous — there is no principal to check, no [Authorize] to lean on — so for a while the cart's uniqueId was the only thing standing between a stranger and somebody else's attendee names, email addresses and prices. A secret URL is not authorisation. Ids leak in ordinary, non-malicious use:

How the id escapesWhat an unguarded route would have granted
Buyer pastes the wizard URL into a support ticket; an agent screenshots it. GET /api/events/cart/{id} returns every attendee's full name, email, phone and the amounts — to anyone who reads the ticket.
The URL reaches request logs, an APM trace, an analytics pipeline, or a referrer header on a third-party asset. Anybody with log or dashboard access — vendors included — could replay the cart, mutate its lines, or drive /checkout/intent.
A shared or kiosk machine keeps the id in browser history. The next person resumes a stranger's registration and pays with the previous buyer's attendee data attached.
An attacker harvests ids from any of the above and scripts them. Bulk extraction of buyer and attendee personal data across an organizer's entire event — a reportable breach, not an inconvenience.
The id still identifies the cart. It no longer authorises anything. The signed cookie does, and a browser only ever returns a cookie to the origin that set it — so a copied URL is inert wherever it lands.

POST /api/events/cart issues a signed capability as an http-only cookie, and RequireCartCapabilityAttribute refuses every later cart-scoped and checkout-scoped call without it. The cheque route is organizer-authenticated and is deliberately not gated on a buyer's cookie.

Token{cartUniqueId:N}.{expiryUnix}.{base64url-signature}, signed HMAC-SHA256 and compared with CryptographicOperations.FixedTimeEquals.
CookieIdealiEventCart_{cartUniqueId:N} — HttpOnly, Secure, SameSite=Strict, path-scoped to /api/events/cart so a capability never rides along on an unrelated API call or into a log of one. One cookie per cart, so two carts open in one browser do not evict each other.
BindingThe token carries its own cart id, so renaming a valid cookie onto another cart fails the signature check.
LifetimeCart expiry plus a 60-minute grace. A card authorised just after the hold lapsed must still be confirmable.
VerificationStateless. Nothing is stored server-side — no session table, no Redis. The signing key is the only shared state, which is why every instance in one environment must carry the identical key.
RefusalOne 403 with errorCode: "cart_capability_required" and one message for every case — no cookie, wrong cart, expired, forged, cart that never existed — so the endpoint cannot be used to enumerate carts.

EventCartCapability:SigningKey must exist before the API can start. It throws on a missing or under-32-byte value on purpose: a default fallback key is a known key, and a known key lets anyone mint a valid capability for any cart — worse than no gate at all, because it looks guarded. 

# Windows PowerShell 5.1 — 48 random bytes, base64
$b = New-Object byte[] 48; ([System.Security.Cryptography.RNGCryptoServiceProvider]::new()).GetBytes($b); [Convert]::ToBase64String($b)
// Configuration/secrets.json — gitignored, never commit a real value
"EventCartCapability": { "SigningKey": "<generated value>" }

One value per environment — local, staging and production each get their own, because the key mints valid tokens for every cart and staging is always the weakest of the three. Identical across every instance within one environment. Staging and production keys are generated inside the secret store itself and pasted nowhere else. The generation command also lives in docs/README.md in the API repository.

What breaks without it, and how each failure presents:

SituationSymptom
Key missing or too shortThe process throws at startup with the setting name in the message. The API does not serve traffic — deliberately, rather than serving registration ungated.
Two instances behind one load balancer hold different keysInstance A sets a cookie, the next request lands on B, and B reads it as forged. Intermittent 403s that look like session loss and never reproduce locally.

What the frontend does with a refusal

A refused capability is terminal. The cart cannot be repaired from the browser — the cookie is http-only, the server will refuse every later call on that cart identically, and it will not say which of the five causes applied. So the wizard does not retry and does not surface the raw failure inline.

DetectionisCartSessionLostError in src/utils/errors.ts. Matches 403 plus cart_capability_required. The failure envelope arrives PascalCase and never passes through camelizeKeys, so both spellings of the error-code field are read.
ReactionuseRegistrationCart drops the cart id, coupon, buyer identity, any buffered line changes and the stored cart id, then raises isSessionLost. Keeping the cart would leave the buyer retrying against one the server will never accept again.
What the buyer seesA single-action "Registration session ended" dialog. The only button reloads the form. There is no retry, because nothing can be retried.
WordingFixed client-side, not read from the response. The server's message is deliberately identical for every cause, so echoing it adds nothing and couples the copy to the API.
Not this pathRestoring a cart id from storage on page load. That failure clears the stored id silently and shows a clean form — a returning buyer with a dead cookie has done nothing wrong and should not meet an error.
Any other failureLeft alone. A 500 or a rejected coupon keeps the cart intact and retryable.
Adding a new anonymous cart-scoped action without [RequireCartCapability]. It reopens the entire hole above, and only the reflection test in RequireCartCapabilityAttributeTests will notice — nothing else in the build will.

Two gates you will meet everywhere

EnsureCartOpen Used before editing. Refuses if the invoice is not PendingPayment, or if any payment already succeeded.
EnsureCartPayable Used before paying. Only checks the status — a live attempt does not block replacing it, because a buyer who abandoned Stripe's dialog cannot cancel it themselves.

Every editing call also runs EventPaymentAttempts.ReleaseAbandonedAttemptsAsync first, which voids a stale Stripe attempt so the buyer is not locked out of their own cart.

Where oversell is prevented

Browsing cart lines are intentionally lightweight: they validate against current availability, but they do not queue every buyer behind the ticket type and they do not make the event look sold out. The real inventory claim happens in EventSeatClaim.ClaimAsync, called by /checkout/intent, /checkout/cheque, and by /checkout/confirm for free orders.

  1. Apply a short SQL lock wait. SET LOCK_TIMEOUT 3000 keeps a rush from tying up request threads and pooled connections for the full command timeout.
  2. Lock ticket types in sorted order. Each distinct ticket type is read with UPDLOCK, HOLDLOCK, so two buyers cannot both read the same last seat as available, and multi-ticket carts avoid lock-order deadlocks.
  3. Re-read availability inside the same transaction. The winner stamps PaymentStartedUtc and extends the hold into payment grace. Losers get a truthful sold-out or reduced-quantity message and no payment intent.
  4. Raise money only after the claim. The shared Invoice, charge rows and payment attempt are created only for carts whose seats survived the claim.
The guarantee is no oversell and no half-charged loser. A buyer can still lose the race, hit the 3-second contention cap, or be asked to retry; that is expected behaviour under load, not a blocker or a server failure.
Adding or removing a line calls TicketingShared.ResetPricingAsync, which throws away the previously calculated charge lines. Any total the frontend is holding becomes stale the moment the cart changes. Always call /price again before showing a total.

6. How the total is calculated

This is the part people get wrong most often, so follow the order exactly. It is applied by EventCartPricingService.PriceCartAsync and the arithmetic lives in BuyerChargeCalculator.

Where each number comes from

ComponentSource row and fieldHow it is calculated
Line price TicketPricePeriod.Amount if a period applies, otherwise TicketType.FullPrice unitPrice × quantity, rounded to 2 decimals.
Membership discount SessionMembershipDiscount.DiscountType, .DiscountValue, .MaxDiscountAmount — reached through SessionMembershipType for the member's active membership type Percentage of the line total, or a fixed amount. Capped at MaxDiscountAmount and never more than the line itself. Applies only when the caller is a signed-in member with an Active membership.
Coupon discount DiscountCoupon, validated by DiscountCouponService.ValidateCouponForEventAsync; recorded on EventInvoice.DiscountCouponId and .CouponDiscountAmount Calculated against the total after the membership discount, then spread across lines in proportion to each line's net. The last line absorbs the rounding remainder so the parts always sum exactly.
Event charge rule EventChargeRule joined to OrganizerChargeRule — fields .CalculationType, .Value, .Label, .ChargeKind Fixed uses the value as-is; Percent is netSubtotal × value ÷ 100. Only rules where EventChargeRule.IsEnabled and the underlying OrganizerChargeRule.IsActive are counted. Ordered by DisplayOrder.
Revenue plan — buyer AdminFeePlanRule where RuleAppliesTo = Buyer, resolved via AdminRevenuePlanAssignment for the organizer and the Event module Same Fixed/Percent formula, on the same net subtotal. Becomes a visible charge line on the invoice.
Revenue plan — organizer AdminFeePlanRule where RuleAppliesTo = Organizer Same formula, but written only as a PaymentChargeSnapshot with no InvoiceItem. The buyer never sees it and it never touches TotalAmount.
Processor fee OrganizerPaymentProcessorFee matched on organizer, merchant and PaymentProductId — fields .ValueType, .Value, .Label Method-dependent, so it differs per payment method. A percentage is charged on netSubtotal + all other buyer charges; a fixed amount is calculated on netSubtotal alone. Quoted per method by /price, and only written to the invoice once a method is chosen at /checkout/intent.
Every charge is written twice: as an InvoiceItem with ItemType = Charge, which is what makes up the money owed, and as a PaymentChargeSnapshot, which records why that amount was charged — the rule, its value, its label and the currency, frozen at that moment. Editing the rule later never changes an existing order.

The application fee

Separate from all of the above, and easy to confuse with it. When the payment intent is created, CalculateApplicationFeeAsync sums the PaymentChargeSnapshot rows whose SourceType is RevenuePlanRule — both buyer-target and organizer-target — and passes that as Stripe's ApplicationFeeAmount. That is the platform's revenue, taken from the transaction.

The organizer's own charge rules and the processor fee are never part of the application fee. The processor fee exists to make the organizer whole for Stripe's cut; handing it to the platform would take it twice. The figure is read from the persisted snapshots, never recalculated.

Pricing is re-runnable

Calling /price twice must not double the charges, so it starts by calling ResetPricingAsync to remove the previous run's charge lines and snapshots before rebuilding them. Without that, the duplicate charge lines leave a balance the payment cannot clear, the invoice lands on PartiallyPaid, and ticket issuance is then refused on an order that was actually paid in full.

7. Attendees, questions and files

When are attendee details required?

The flagSession.RequiresAttendeeInfo, set by the organizer in the session wizard.
How the page knowsvisibleTabs contains "attendee-info" when any session in the event has the flag. GET /register/attendee-info then returns only those sessions.
What is storedOne EventInvoiceItemAttendee per seat, with a SlotIndex. Submitted per line, before payment.
The rule at submitThe number of attendees must equal the line quantity exactly, and each needs a name. Email and phone are optional.
Length limitsName and email are bounded to 255 characters, phone to 50 — the same widths as the columns they land in, so an over-long value is refused at the boundary rather than at SaveChanges.
What happens at issuanceSlot n becomes ticket n's attendee. A submitted slot owns all its fields — a blank email means "not provided", it does not fall back to the buyer's. If no attendees were submitted at all, the tickets carry no attendee name.
Attendee details are not enforced at payment time. Only the questionnaire is. If a session requires attendee info, the frontend must collect it — the server will happily issue nameless tickets otherwise.

When does the questionnaire appear?

Two independent sources, both authored by the organizer against the event:

SourceWhere it comes fromAnswered by
Custom form EventForm → CustomForm → CustomFormField. Forms are reusable and shared with Membership. formResponses[], keyed by fieldUniqueId. Stored as EventPurchaseSubmissionValue.
Custom question EventQuestion with its EventQuestionOption rows, defined directly on the event. questionResponses[], keyed by questionUniqueId. Stored as EventQuestionResponse.

The tab appears when the event has at least one active question, or at least one form that actually contains a field. A form with no fields renders nothing, so it deliberately does not put an empty tab in front of the buyer.

Answers are per order, not per ticket. Ten tickets in one cart produce one set of answers, because the organizer authored the questions against the event.

Where the requirement is enforced

Submitting answers is a separate call, so a caller could simply never make it. EventAnswerRequirement.EnsureRequiredAnswersPresentAsync therefore runs at the money, not at the answers — inside /checkout/intent, /checkout/cheque, and inside /checkout/confirm for a zero-total order. It refuses with the organizer's own RequiredMessage when one was written.

A mandatory field counts as answered when it has either a non-empty AnswerValue or a FileStorageId — an uploaded file is an answer in its own right.

Answer files, and why they are cleaned up

A file is uploaded the moment the buyer picks it, long before there is an answer to attach it to. So the upload records an EventAnswerFileUpload row marking it in flight.

  1. Upload. UploadAnswerFileAsync validates the extension against the field's AcceptedFileTypes, refuses executables whatever the organizer typed, saves the blob, and writes the in-flight row.
  2. Submit. SubmitAnswersAsync binds the fileStorageId to the answer and deletes the in-flight row — the file now belongs to an order.
  3. Sweep. Anything still marked in flight 24 hours later was abandoned. EventAnswerFileCleanupService deletes the blob and soft-deletes the FileStorage row, unless an answer claims it after all.

The 24-hour grace is far longer than any ticket hold, so a buyer still filling in the form never loses their file. The frontend has nothing to do here — no delete call, no cleanup on unload.

8. Payment and settlement, step by step

What the webhook does, in order

  1. Verifies the signature against the webhook secret from system settings. An unsigned or mismatched body is rejected.
  2. Reads the metadata on the payment intent. The intent was created carrying ModuleId = Event and ModuleEntityUniqueId = the invoice's uniqueId. Without that metadata the webhook returns success and does nothing — which is how other systems' intents are ignored.
  3. Settles the invoice through the shared invoice service: allocates the payment and moves the invoice to Paid.
  4. Routes to the module. For Event, EventPaymentSettlementService.HandlePaymentSucceededAsync.
  5. Records how it was paid — before the issuance gate, so even an order that ends up in recovery still has its payment source.
  6. Checks the issuance gate. If the invoice did not reach Paid, it logs loudly and queues the order for recovery rather than silently leaving a paid buyer with nothing.
  7. Issues tickets, one line at a time, each in its own transaction so one bad line cannot deny tickets to the rest of the order.
  8. Redeems the coupon — a coupon is only spent when an order actually settles.
  9. Queues the emails and returns. Never awaited: a slow handler makes Stripe time out and retry a payment that already succeeded.
A redelivered webhook is safe. Issuance is idempotent — a line that already has its full set of tickets returns the existing codes instead of minting new ones — and the handler deliberately re-enters settlement on a repeat success event, because the first delivery may have settled the invoice and then failed before issuing.

Why two simultaneous intents for one cart collapse into one

EventCheckoutIntents.BuildIdempotencyKey derives the key from the cart, the chosen method and the invoice's payment count — event-cart-{cartUniqueId}-{method}-{paymentCount} — and StripeService.CreateEventPaymentIntentAsync carries it on its own RequestOptions instance, separate from the one handed to the customer lookup, because Stripe rejects a key replayed against a different call's parameters. A request that arrives without a key is refused with an ArgumentException before Stripe is reached: a caller that omits it is asking for a fresh intent on every retry, which is how one cart ends up with two payable intents.

The count in the key is what keeps it from being too sticky. Retiring the live attempt writes a payment row, so the next genuine attempt hashes to a different key and gets its own intent, while a duplicate of the attempt in flight does not. Selecting a second method also produces a different key, since the method is part of it. Covered by StripeEventIntentIdempotencyTests and by the simultaneous-request, retired-attempt and second-method cases in EventCheckoutServiceTests.

Why /checkout/confirm exists as well

Webhooks are not instant and, in a local or test environment, may never arrive at all. ConfirmCheckoutAsync gives the buyer their tickets without waiting: it settles any open attempt, re-reads the invoice, and if issuance is authorised runs exactly the same issuance code. Whichever path arrives first wins; the other finds the work already done.

Issuance is authorised when any of these is true (TicketingShared.IsTicketIssuanceAuthorised):

  • the invoice status is Paid;
  • TotalAmount is zero or less — a free order;
  • a cheque payment exists that has not failed — and only an organizer-authenticated endpoint can record one.

What checkout refuses, and what each refusal means

None of these is a server error. Every one of them rolled its transaction back, so the buyer was not charged and the call is safe to repeat. They arrive as an ordinary failed envelope — success: false with a message written for the buyer to read.

The messageWhere it comes fromWhat the buyer should do
"Cheque payments are recorded through the cheque endpoint." DescribeUnsupportedMethod — a method this endpoint cannot start Call POST .../checkout/cheque instead, signed in as the event's organizer. Checked before the seat claim, so nothing was held: a refusal decided by the method alone must not take seats out of circulation for a call that could never have succeeded.
"Someone else is booking these tickets right now. Please try again." TicketingShared.ConcurrencyRetryMessage — the seat claim lost the row lock, or was chosen as the deadlock victim Press pay again. Stock still exists on every line; the request simply queued behind another buyer and gave up after the 3-second cap.
"'Early Bird' sold out before your payment could be taken. Your order was not charged." DescribeSeatContentionAsync — the same lost race, but the availability read afterwards found nothing left on that line Nothing. Retrying cannot help. Send them back to the ticket picker.
The organizer's own message, or a validation sentence Any InvalidOperationException raised inside the transaction — an expired hold, a missing required answer, a quantity no longer available Fix what the sentence names, then price and pay again.
Stripe's decline message, quoted verbatim DescribeStripeFailure on a card_error Use a different card. Stripe writes these for cardholders, so the wording is already theirs.
"Payments are busy right now. Please wait a moment and try again." DescribeStripeFailure on a rate_limit_error or HTTP 429 from Stripe Wait a few seconds and press pay again — and note that the seats are still held, because the claim committed before Stripe was called. Do not send this buyer back to the ticket picker.
"Payment could not be started. Please try again." Any other StripeException, or a DbUpdateException Retry once. Stripe's own message is deliberately withheld here because it carries account, customer and request ids.
The seat claim and the Stripe call are on opposite sides of a commit. A buyer refused by the claim holds nothing; a buyer refused by Stripe holds their seats until the reservation expires or ReleaseAbandonedAttemptsAsync clears the attempt on their next cart write. The two refusals read alike and behave differently — do not collapse them into one handler.

When payment fails

HandlePaymentFailedAsync cancels every still-Active reservation on the order and refreshes the ticket-type counters, putting the seats straight back on sale. Tickets that were already issued are never revoked here — reversing a fulfilled order is a refund, not a side-effect of a failed attempt.

11. Registration-specific traps

The trapWhat actually happens
Showing a total without calling /priceThe cart's totalAmount is only the subtotal until pricing runs. No charges, no processor fee.
Caching the total across a cart editAdd or remove a line and the charge lines are wiped. The stale total will not match what the intent charges.
Using the same total for every payment methodProcessor fees differ per method. That is the entire reason /price returns an array.
Sending stripeAccount when it came back nullACH and PAD live on the platform account. Confirming against a connected account fails.
Treating isSettled: false as a failureBank payments are legitimately pending for days. Send the buyer to the order page.
Polling the order page on your own timerpollAfterSeconds reaching zero is the stop signal, and the endpoint is rate-limited to 60 per minute per IP.
Passing the InvoiceItem id as the line idRoutes expect the EventInvoiceItem's uniqueId — the lineUniqueId the cart returned.
Submitting fewer attendees than the line quantityRefused outright. It must be exact.
Skipping the answers callIt is not enforced at the answers endpoint — it is enforced at payment, where the buyer is refused with the organizer's own message.
Refunding because a ticket email failedThe order is intact. Use the organizer's resend endpoint.
Sending a cheque to /checkout/intentThat route only starts Stripe payments. Cheque has its own organizer-authenticated endpoint, and one call there records the payment and issues the tickets — no intent, no confirm, no Payment Element.
Showing a cheque order as fully paidThe tickets are issued while the invoice stays owing. amountDue comes back non-zero on purpose and has to be shown.
Treating a refusal as a server errorEvery refusal at /checkout/intent comes back as a normal failed envelope with a buyer-readable message. A 5xx from that route is a defect, not a busy ticket type.
Sending a throttled buyer back to the ticket picker"Payments are busy right now" means Stripe refused after the seats were already claimed. The buyer still holds them; retrying payment is the whole fix.
Retrying "sold out before your payment could be taken"That wording is only chosen once availability has been re-read and found empty. Retrying cannot succeed.
Expecting a shared Invoice while the cart is openAn open cart is an EventInvoice only. The shared invoice and its order number are minted at /checkout/intent, so orderNumber is null until payment starts.
Pointing Stripe at /webhooks/stripeThat route only logs. The real one is /api/public/stripe/web-hook.
Deploying without EventCartCapability:SigningKeyThe API does not start. There is no default key on purpose — see "Who is allowed to touch a cart".
Treating the cart id as proof of ownershipIt never was. The capability cookie is the credential; a cart id passed to another browser, device or email link opens nothing.
Reading 403 cart_capability_required as "cart not found"It says nothing about existence, deliberately. Send the buyer back to the event page to start again; do not retry.

How to regenerate

  1. Refresh the route table if endpoints changed. In the backend repository, remove the Skip from tests/Ideas.API.Tests/EndpointInventoryDump.cs and run: 
    $env:ENDPOINT_DUMP_PATH = "<this-repo>/docs/tools/endpoints.reflected.json"
dotnet test ./tests/Ideas.API.Tests/Ideas.API.Tests.csproj \
  --filter FullyQualifiedName~EndpointInventoryDump
    Put the Skip back afterwards.
  2. Refresh the documentation comments: 
    cd docs/tools
node extract-summaries.mjs summaries.json
  3. Rebuild both documents — they share the narrative, so always do both: 
    node build-registration-doc.mjs ../event-registration-backend.bootstrap.html
node build-backend-doc.mjs ../backend-developer-handbook.bootstrap.html
Want a better one-line description beside a route? Do not edit the generated HTML — it will be overwritten. Write a /// <summary> comment above the controller action instead. It then serves the code and both documents at once, and can never disagree with the code it sits on.
Regenerate in the same commit as the change that made it necessary. A separate "update the docs" task is a task that does not happen.
