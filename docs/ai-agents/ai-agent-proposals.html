Executive summary

Ideali earns on transactions, not subscriptions. Module access carries no price in the system; revenue comes from tips, per-transaction platform charges and event fees. That makes the organizer the whole business. An organizer who gets live faster, runs their operation with fewer people and asks more of the platform generates more volume — and our revenue is a percentage of that volume.

So the question this document answers is narrow: where does AI make an organizer meaningfully faster in a way that writing more backend code cannot?

The honest answer is: in fewer places than an AI proposal usually claims, but in a handful of places it is transformative. Seven agents qualify. Three more are hybrids where conventional code does the work and AI handles the last mile. And roughly a dozen things I would have been tempted to call agents are simply features we have not built — they are listed by name, because presenting them as AI would be misleading and would let real gaps hide behind a more exciting label.

One short foundation item comes first: AI in the product today has no authentication, permission, quota or cost tracking around it.

Why an agent, and not more backend code

This is the right challenge to put to any AI proposal, and most of what gets pitched as AI fails it. The test is simple: can the rules be written in advance? If the input has a fixed shape and the logic can be enumerated, conventional code wins on every dimension that matters — cost, speed, reliability, testability. AI should be reached for only when one of those conditions genuinely breaks down.

Backend code wins when…
  • The input has a schema — dates, amounts, statuses, identifiers
  • The logic can be written as rules, however many
  • The same input must always give the same output
  • It must be provably correct — anything touching money or permissions
  • It runs constantly and cheaply at volume
An agent earns its place when…
  • The input is language, a document or an image — no schema exists
  • The output is language written for a person to read
  • The possible inputs are unbounded, so rules cannot be enumerated
  • Intent must be translated — what someone meant into what the system does
  • The variety is a long tail no team could staff against
The commercial version of the same point. Backend code scales with engineering effort — each new capability costs another build. AI scales across the long tail: one agent handles every phrasing an organizer might use, every organization's tone of voice, every question a member might ask. Where the tail is short, write code. Where the tail is infinite, an agent is the only economic answer.
Applied honestly, this rules out much of what gets called AI. A view joining a supporter's giving, membership and attendance is a database query. Churn and lifetime value are calculations. A work queue is a table and a scheduled job. A suppression list is a column. Cart-recovery timing is a timer. All of those are real gaps in our product and all of them should be built — as backend features, on the engineering roadmap, at a fraction of the cost. They are listed in full further down.

The organizer's day today

Every proposal below is aimed at one of these. All were verified in code during the review.

Getting live takes 28 screens

Publishing one event with one session and one ticket takes 28 screens and around 49 fields — and requires a payment account and venue that already exist, which nothing tells them in advance.

The product is hard to learn and does not explain itself

85 permission settings with non-obvious wording, constraints that only surface as validation errors, and two setup steps that are not implemented at all.

Answers live in Excel, not in the product

Nine export buttons exist, each returning only the current page of fifty rows. Anything resembling analysis happens in a spreadsheet outside our platform.

Everything written starts from a blank page

One editable email per campaign, event or membership tier, no preview against real data, no library, no reuse — and no help in the Events product at all.

Reading is the job

Approving one applicant means opening several pages and each uploaded document in turn. Poll free-text shows three answers. Event registration answers cannot be read at all.

Members email the office

Document search matches category names only, so routine member questions — expiry dates, receipts, what a policy says — land on the same staff we are trying to free up.

Where AI is the only answer

Seven agents. Each includes a plain statement of why backend code cannot substitute — that claim is the point of the proposal, so it is stated explicitly rather than assumed.

01 · Organizer · All modules
Setup Copilot
Start
The problem

Twenty-eight screens and roughly forty-nine fields to publish one event with a single session and ticket. Prerequisites that block at step six with no warning at step one. No completeness check before going on sale, so events reach the public with no tickets or no payment account attached. And because the flag marking setup complete is never set anywhere in the code, we cannot even see who gives up or where.

The agent

The organizer describes what they are running in their own words. The agent produces a complete draft configuration across every step — sessions, tiers, pricing schedule, dates, questions, confirmation email — which they review and adjust rather than author. It raises prerequisites at the start, not as a blocker, and checks readiness before anything goes live.

What it owns
  • A full draft setup generated from a plain description
  • Prerequisites surfaced up front instead of blocking mid-flow
  • Readiness check before publishing, which does not exist today
  • A staff role proposed from a job description rather than 85 settings
Why not code: we can cut 28 screens to 12 with better engineering — worth doing regardless. We cannot write rules that turn any sentence an organizer might type into a valid configuration. The input space has no schema and no boundary.
Evidence: publish gates check only current state, never completeness. Two setup steps return "not implemented". The wizard-completed flag is never set to true anywhere in the codebase.
02 · Organizer · All modules
Organizer Success Copilot
Start
The problem

The product is large and does not explain itself. Rules surface only as validation errors — a hundred-seat show cannot offer a hundred-ticket order, and nothing says so until the save fails. Permission wording is ambiguous enough that roles get configured wrongly. Onboarding is finished by our own staff by hand, because module selection, branding and sender configuration are reachable only through our admin console.

The agent

An in-product expert that answers "how do I", "why can't I", and "what does this do" — grounded not in generic documentation but in that organizer's actual configuration. It can explain why an event will not publish by looking at the event, and walk them through the fix.

What it owns
  • Answers product questions in the context of this organizer's own setup
  • Diagnoses "why can't I publish / why did this fail" concretely
  • Explains settings and permissions in plain terms before they are chosen
  • Reduces the manual finishing work our team does on every new account
Why not code: the code answer is documentation and better error messages — both worth doing. Neither can answer an unanticipated question, and neither can reason about this organizer's specific configuration to explain what is actually wrong.
Evidence: module selection, logo and sender configuration are admin-only, so every self-serve signup requires our staff to finish it. Signup via single sign-on produces an organization with no portal address at all.
03 · Organizer · All modules
Ask Ideali
Start
The problem

Organizers cannot ask our product questions. There are nine export buttons and each returns only the current page — fifty rows — so real analysis happens in a spreadsheet outside our platform. The member list has no date filters at all, which means the single most common question in membership, "who lapses this month", cannot be asked at all.

The agent

A question box over their own data. They ask in their own words — "members who lapsed last year and gave over five hundred", "which sessions are underselling with a fortnight to go" — and get an answer, a table they can act on, and the ability to follow up. Every answer states what it counted so it can be trusted.

What it owns
  • Plain-language questions answered against live data, no export step
  • Follow-up questions that keep the context of the previous answer
  • Results usable directly — a list to act on, not a file to open elsewhere
  • States its own method so figures can be checked
Why not code: partly it is — the metrics and filters underneath must be built properly as backend work, and that is on the list below. But no filter set anticipates every question. Code gives an organizer controls they must first learn; the agent removes the learning.
Evidence: every export endpoint exports the current page only. No churn, retention or lifetime-value calculation exists anywhere in the platform.
04 · Organizer · All modules
Content Studio
Next
The problem

We already generate campaign descriptions and banner images and organizers use it — but it exists only in donations, runs off a single fixed instruction, and is entirely absent from the Events product. Everywhere else our customers write from nothing: one editable email per campaign, event or tier, no preview against a real record, no library, no reuse. Every shared campaign link carries the same generic description regardless of the cause.

The agent

Extends generation across all three modules and beyond descriptions into confirmation emails, announcements and share text — written in each organization's established voice, aware of the personalization fields available, and previewable against a real record before it goes anywhere.

What it owns
  • Drafts descriptions, emails, announcements and share copy in every module
  • Matches each organization's own tone rather than one generic voice
  • Preview against a real record before sending
  • Alternative subject lines and share text where they affect conversion
Why not code: the code answer is a template library — and a template cannot sound like a particular organization writing about a particular cause. Covering that with templates means one per organization per module per message type. That is the long tail.
Evidence: existing AI is one service with a single hardcoded fundraising instruction, used at three points in the older product and nowhere in Events.
05 · Organizer · Membership
Application Reader
Next
The problem

Approving one applicant means opening their detail page, then their form answers on a second page, then each uploaded document in turn — and deciding by reading. Nothing is pre-checked or compared against previous decisions. Approvals record no rationale at all, so the reasoning behind past decisions is simply gone and consistency between reviewers is impossible to hold.

The agent

Reads the whole application — written answers and uploaded documents — before a human opens it. Produces a short summary, flags what needs attention, and drafts a recommendation with its reasoning. The staff member confirms or overrides. The agent never decides.

What it owns
  • One-screen summary of an application spanning several pages and files
  • Reads uploaded evidence rather than just listing that a file exists
  • Drafts the recommendation and, where declined, a considerate reason
  • Captures rationale on approval too, building the missing audit trail
Why not code: code can flag a duplicate email address — and should. It cannot read a personal statement, interpret a certificate image, or weigh either against a policy written in prose.
Evidence: approve and reject share one status path; approval passes an empty reason. Rejection reasons arrive as an unvalidated web-address parameter.
06 · Organizer · All modules
Community Insight
Next
The problem

We store a great deal of what people actually wrote and read almost none of it. Poll open-text questions display three answers while every other question type is fully analysed. Application essays are readable one applicant at a time. Staff notes on invoices are an organization's real working memory and are never read across records. An organization can ask four hundred people what to improve and have no practical way to find out.

The agent

Reads every free-text source and returns themes, sentiment and movement over time — what people are asking for, what is changing, and which individual responses a human needs to see. Always links back to the original words so staff verify rather than trust.

What it owns
  • Themed synthesis of poll, survey and application free text at any volume
  • Trends across time and across membership segments
  • Flags individual responses needing a personal reply
  • Every finding traceable to the responses behind it
Why not code: prose has no schema. Counting and grouping work on ratings and choices — which is exactly why those are already analysed properly and free text is not. There is no query that summarizes four hundred paragraphs.
Evidence: poll open-text is limited to three sample answers. There is no poll export endpoint of any kind.
07 · Members · Frees organizer staff
Member Self-Service Assistant
Later
The problem

Organizations upload handbooks, bylaws, minutes and forms for their members, and the only way to find anything is matching text against a category name — there is no search inside documents at all. Members who cannot find an answer email the office, so the routine questions land on exactly the staff the other six agents are trying to free up.

The agent

Answers members' questions from their own record and their organization's published documents, with citations, respecting precisely what that member is entitled to see. Hands to a person whenever it is not confident.

What it owns
  • Questions about the member's own membership, giving and receipts
  • Answers drawn from the organization's documents, with citations
  • Strictly respects existing document permissions and view-only rules
  • Hands off to staff rather than guessing when unsure
Why not code: full-text search is the code answer and is worth building. Search returns documents; members are asking questions. "Can I bring a guest to the AGM" is answered by a clause on page nine, not by a list of files.
Evidence: document search matches against the category name only. No search of document content exists anywhere in the platform.

Where AI is only the last mile

Three cases where the bulk of the value is conventional engineering and AI contributes something narrow at the end. Worth doing — but the backend work is the substance, and should be scoped and funded as such.

Hybrid · Revenue recovery
Recovery outreach

Code does: detect the failed charge, the abandoned cart, the approaching expiry; schedule and send; check availability. All ordinary work, none of it built today.

AI does: write the message so it is worth receiving, and decide which cases deserve a person rather than an email.

Recurring gifts end in a permanent failed state with no recovery path; abandoned carts are detected every minute and nothing follows them up.
Hybrid · Finance
Reconciliation

Code does: match on amount, date and reference; maintain an outstanding-and-aging view; capture payment details on event orders as membership already does.

AI does: interpret messy bank descriptions and free-text notes where an exact match fails.

Membership revenue is reported on invoice creation date, not payment date, so it cannot tie to a bank statement.
Hybrid · Event day
Event run-sheet

Code does: expose the registration answers at all, total the dietary and accessibility counts, produce per-session manifests, read back the check-in log.

AI does: interpret free-text special requests and group them into actions for the team.

Registration answers have no organizer-facing read path. The check-in log is written at four points in the code and read at none.

Foundation needed first

AI foundation & governance Start — prerequisite

AI in the product today is a single service reached through an endpoint with no authentication, no permission, no quota and no cost tracking. Nothing records what was generated, for whom, or at what cost, and there is no way to grant or withhold the capability per customer. Acceptable for three experimental fields; not acceptable underneath seven agents touching member data.

Before the first agent ships: authentication and permissions on AI features, per-customer quotas and cost attribution, an audit record of every agent action, a managed home for instructions rather than values compiled into code, and a consistent approval model so agents propose and humans decide wherever money or a person's status is involved.

It is also what makes AI sellable — entitlement and quota are the difference between a cost we absorb and a capability we can package and charge for.

Raised separately, not part of this proposal. The review also found three endpoints that send email, spend money on AI, or fetch arbitrary web addresses with no authentication at all, plus a payment-related endpoint marked publicly accessible whose backing service file is empty. These should be ticketed and fixed on their own merits regardless of any decision about AI.

Constraints & caveats

We have transaction data, not behaviour data

No general activity log or click tracking exists. Agents can reason about what people bought, gave and joined — not what they browsed. The proposals stay inside that boundary deliberately.

Three agents depend on backlog items first

Ask Ideali needs the metrics layer built. The run-sheet needs registration answers exposed. Self-service needs document content indexed. These are prerequisites, not assumptions.

Data quality will cap early accuracy

Contact matching is not reliably scoped per organization, and two dashboard figures are computed misleadingly. Agents built on this inherit those flaws until they are fixed.

Sequencing matters more than count

The first three are chosen because they need the least backlog work and touch the organizer's day most directly. Adopting all seven at once is not the recommendation.

Method

Output of a direct review of the production backend (Donation, Membership, shared invoicing and payments) and the in-development Event module across backend and frontend, conducted August 2026. Findings were traced to specific services, endpoints and configuration rather than inferred from documentation.

This document argues what each agent should own and why code cannot substitute for it. Implementation approach, model selection, guardrails, effort and staffing are deliberately out of scope. The Event module is moving quickly; anything relating to it should be re-validated against the code before work is scoped.
