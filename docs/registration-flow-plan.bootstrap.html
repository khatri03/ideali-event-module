Event registration: making the checkout real

The registration route reads data and never writes any. The database already models the entire purchase. This plan connects the two.

/events/:eventUniqueId/register sohail/features/event/event-registration 29 Jul 2026

Where we are

The registration wizard loads an event through six read-only endpoints — one per tab — and renders six steps: Description, Sessions, Buyer/Attendee info, Attendee Info, Questionnaire, Payment. Selecting tickets, entering buyer details, choosing a payment method and entering card data all work. Then handleConfirmPurchase validates the form, closes the dialog and fires a success toast.

No network call. Nothing is saved. No ticket is issued, no inventory is held, no money moves. Every pricing and eligibility rule the buyer sees is computed in the browser from a payload that may be stale, including the subtotal that the server then trusts when it calculates fees.

The one that matters commercially GET /register/payment?subtotal=N takes the order total from the client and computes charge rules, revenue charges and processor fees on top of it. The number is editable by anyone. Every fee in the system is derived from it.

Plan

Sequential — each phase depends on the one before it.

Integration test across reserve → invoice → confirm. Fix the EventInvoiceItem persistence gap. Check the stock counters against TicketsOnHold / AvailableForSale / TicketsSold. No new features. Nothing below is trustworthy until this is green.

A Draft invoice becomes the cart. Endpoints to create it, add and remove lines, and read its state. Each line drives its own reservation, so holds are real. The countdown comes from the event's PurchaseTimeLimit as an absolute UTC deadline the UI only displays. Order id in an httpOnly cookie and in the response body.

One pricing service: active price period, membership discount, coupon, min/max and availability checks, event charge rules, buyer revenue charges, processor fee per method. Results written to InvoiceItem and PaymentChargeSnapshot. The subtotal query parameter is removed — the server reads its own order.

Per-slot attendees onto EventTicket. Questionnaire answers into SessionPurchaseSubmission and its children. Required-field validation enforced server-side from SessionQuestion.Required.

PaymentIntent carrying the invoice id in metadata, following the membership payment service already in the codebase. The webhook becomes authoritative: it settles the invoice and issues tickets, idempotently. Client confirm becomes a UX fast-path that is safe to run twice. Cheque orders settle as pending with tickets issued.

The server returns the step list, deadline, totals and validation errors; the UI renders them. Client-side tab logic, price display, savings, quantity limits, purchase validation, subtotal and timer start are deleted. The questionnaire gets real inputs. The 4,100-line wizard file is split per the repo's own structure rules.

Coupon entry, digital ticket delivery, thank-you email on settlement, refund policies shown at checkout. Seats.io stays out of scope.

Open decisions

Do event-level questions belong in the registration form?

The event wizard collects EventQuestion and EventForm. Registration reads only session questions. Either we wire them in — which needs a storage decision, since SessionPurchaseSubmission hangs off a session line — or the wizard step is dead UI. Product call.

Does anything outside the wizard call checkout/confirm?

Phase 4 inverts its meaning: the webhook issues tickets, and confirm becomes advisory. If another client depends on getting ticket codes back synchronously, that breaks. No other caller found, but worth confirming before the change lands.

Cheque orders — tickets before the cheque clears?

Cheque is organizer-only. The proposal is to issue tickets immediately and mark the invoice pending, so the organizer can register someone on the spot and reconcile later. Confirm that matches how it is used.
