UX Proposal

Custom List Editor

One screen where an organizer sees who is in a list and adds more — without switching mental models.

Recommendation — one table, two tabs

Both jobs (see who's in, put more in) are the same task on the same data: a filterable table of people with checkboxes. Give them the identical table and switch only the source and the bulk action.

  • Tab 1 — In this list. Members already added. Search, pagination, bulk Remove.
  • Tab 2 — Add members. Membership-type filter (required), search, pagination, bulk Add.
  • A selection action bar slides in only when rows are checked. It is the only place bulk actions live, in both tabs.
  • Tab labels carry live counts, so the result of an add is visible without leaving the tab you're in.

Below 768px the table becomes a card list. Four columns cannot survive 390px without either horizontal scroll or truncation, and the primary action becomes a sticky full-width button — thumb reachable, 44px tall.

Alternatives considered and rejected

Dual-pane transfer list (available → selected)

The classic “shuttle” control. Rejected: it halves the horizontal budget on desktop so the membership-type column has to go, and it collapses into two stacked lists on mobile — which is exactly the two-tab design, but reached by a worse route. It also implies the right pane is a staging area you must confirm, adding a save step this feature does not need.

Modal picker on top of the members table

What the current build effectively does. Rejected: the organizer loses sight of who is already in the list at the moment they most need it, and a modal containing a filter, a search, a paginated table and a bulk action is a page wearing a modal's clothes.

Inline “add” row expanding above the existing table

The current editor. Rejected: two tables with different columns and different pagination stacked vertically on one screen. Users must work out which pagination belongs to which set. The tab strip removes that ambiguity for free.

What this needs from the API

  1. New: GET /custom-list/{uniqueId}/members?searchTerm=&pageNo=&pageSize= — paginated, searchable. Today GET /custom-list/{uniqueId} returns every member inline; at 128 members that is tolerable, at 5,000 it is not.
  2. Add addedOnUtc and membershipTypeName to the member rows returned by that endpoint, so both tabs render the same columns.
  3. No change to add/remove — both already take arrays and are idempotent, which is exactly what a bulk action bar needs.
