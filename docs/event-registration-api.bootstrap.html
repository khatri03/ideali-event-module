Event Registration — Frontend Guide

This guide explains every server call the event registration screens make, in order, in plain language. If you are new to this project — or new to React — read sections 1 to 4 first. They explain the shape of the whole thing. After that you can jump to whichever call you are working on.

What are we building?

A public page where someone buys tickets to an event. They do not log in. They open a link, pick tickets, type their details, pay by card or bank transfer, and then see a confirmation page. Tickets arrive by email as PDF files.

That is five screens, roughly:

  1. Description — what the event is about.
  2. Sessions — pick which tickets and how many.
  3. Buyer / Attendee info — who is paying, and who is coming.
  4. Questionnaire — extra questions the organizer added.
  5. Payment — see the total, pay.

Then a sixth page, on its own URL: the order confirmation page.

Not every event uses all five screens. Some have no description, no extra questions and no named attendees. The server tells you which screens to show — you never guess. Section 9 covers this in detail.

2. Words you need to know

These words appear on every page below. Learn them once here and the rest reads easily.

Event
The whole thing being sold — "Global Product Summit 2026".
Session
One bookable part of an event — "Day One — Main Stage". An event has one or many.
Ticket type
A kind of ticket inside a session — "General Admission", "VIP". Each has its own price and stock.
Cart
The buyer's in-progress order. It is not a JavaScript array in your component. It is a real record on the server that holds stock and expires. More on this in section 6.
Line
One row in the cart — "2 × General Admission for Day One". Attendee names are attached per line; questionnaire answers belong to the whole order.
Reservation
The hold placed on stock when a line is added. It expires after a set number of minutes. This is what stops two people buying the last seat at the same time.
Invoice / Order
Same thing, two names. Created when payment starts. Unlike the cart, it is permanent. The buyer's confirmation page is built from it.
GUID
A long random id like 8f2a1c44-3f0e-4b53-9a4a-7c0d1e5f22b1. Every public id in this system is one. They are random on purpose — random means unguessable.
Envelope
The wrapper around every server response. The data you want is always inside a data property. See section 3.1.
Stripe
The payment company. Their JavaScript library runs in the buyer's browser and handles the actual card details.
PaymentIntent
Stripe's record of "someone is about to pay this exact amount". Our server creates it and hands you a clientSecret — a one-time token your page gives to Stripe to complete the payment.
Webhook
Stripe calling our server directly to say "that payment went through". It happens behind the scenes, and it is the thing that truly finishes an order. Your page never sees it.
Settled
The money has actually arrived. Cards settle instantly. Bank transfers can take days — so "paid but not settled yet" is a completely normal state you must design for.
Polling
Asking the server the same question every few seconds until the answer changes. Used on the confirmation page while a bank payment settles.
Anonymous endpoint
A server call that needs no login. Almost every call in this guide is one — buyers are not users.
Idempotent
Safe to call more than once. Calling it twice does the same thing as calling it once. Useful when you cannot be sure whether the first call arrived.

3. Rules that apply to every call

3.1 Every response is wrapped in an envelope

The server never sends you the data directly. It always wraps it:

{
  "success": true,
  "message": null,
  "errorCode": null,
  "validationErrors": null,
  "data": { /* <-- what you actually want is in here */ },
  "timestamp": "2026-08-05T09:14:22.881Z"
}
Reading response.data.name and getting undefined. With axios, response.data is the envelope. The event's name is at response.data.data.name. That double data catches everyone once. Use the shared unwrap helper instead of reaching in by hand.

When something goes wrong, the same envelope comes back with the bad news filled in:

{
  "success": false,
  "message": "Discount coupon not found.",
  "errorCode": null,
  "validationErrors": {
    "buyerEmail": ["The BuyerEmail field is not a valid e-mail address."]
  },
  "data": null
}
  • message — one sentence, safe to show the buyer as-is.
  • validationErrors — a map of field name → list of problems. Show each under its own input.

3.2 Property names may be capitalised either way

The same field can arrive as name or Name depending on the endpoint. Do not fight this — every parser in this project already accepts both and picks whichever turned up: 

name: parsed.Name ?? parsed.name ?? ""

Examples in this guide use lowercase. Copy the existing parser pattern and you are fine.

3.3 What each status code means

CodeMeaningWhat your UI does
200It worked.Render the data.
400The server understood you and said no. There is a reason in message.Show message near the thing that failed. This is a normal outcome, not a crash.
404No such order. Only the order-status call returns this.Show the "order not found" card. Stop asking.
429You asked too many times too fast.Slow down. Only the order-status call can return this.

3.4 Two calls are challenged by Cloudflare Turnstile

Registration needs no login, so two calls sit wide open to anyone: POST /api/events/cart, which opens an order, and POST …/checkout/intent, which claims the seats and reaches Stripe. Both require a Cloudflare Turnstile token in a Turnstile-Token header. Every other cart call needs a cart id that only the first of those can hand out, so they are left alone.

You do not add the header yourself. The shared axios client mints a token and attaches it for exactly those two routes. A token is single-use and expires in minutes, so it is minted per request rather than once per session — a wizard sits open far longer than a token lives.

  • VITE_TURNSTILE_SITE_KEY switches it on. Empty means unchallenged, which is how local development runs.
  • Most visitors see nothing. Cloudflare only paints a widget when it wants proof, and it disappears again once solved.
  • A rejected token comes back as 400 with errorCode: "captcha_failed". Show message and let the buyer retry — the next attempt mints a new token by itself.
Caching a token, or reusing one across the cart and the payment call. Cloudflare answers the second use with timeout-or-duplicate and the buyer is blocked for no reason.

3.5 Money

  • Amounts arrive as numbers like 470.61.
  • Display them with Intl.NumberFormat, never with string concatenation.
  • Never add prices up yourself. The server sends you every total you need. Section 6.5 explains why this matters so much.

3.6 Dates

All dates are UTC, in ISO format: "2026-09-14T13:00:00Z". The event also sends a timeZone. Show session times in the event's time zone, not the buyer's browser time zone — otherwise someone in London reads the wrong start time for a Toronto event. Use date-fns. Do not add another date library.

3.7 A reusable call template

Every API function in this project looks like this. Copy the shape:

// src/api/eventOrders.ts
import { z } from "zod"
import { client } from "@/api/client"
import { API_ROUTES } from "@/utils/routes"
import { normalizeEventOrderStatus, type EventOrderStatus } from "@/features/events/schemas/eventOrder.schemas"

// 1. Describe the envelope
const serviceResponseSchema = z.object({
  Data: z.unknown().nullable().optional(),
  data: z.unknown().nullable().optional(),
})

// 2. Pull the payload out of the envelope
function readResponseData(payload: unknown): unknown {
  const parsed = serviceResponseSchema.parse(payload)
  return parsed.Data ?? parsed.data
}

// 3. Call, unwrap, validate, return a clean typed object
export async function fetchEventOrderStatus(orderUniqueId: string): Promise<EventOrderStatus> {
  const res = await client.get<unknown>(API_ROUTES.eventOrderStatus(orderUniqueId))
  return normalizeEventOrderStatus(readResponseData(res.data))
}

Three steps, always: unwrap the envelope, validate the shape with Zod, return a clean object. The rest of the app then only ever sees clean, typed data.

4. The whole journey, in order

Order matters. You cannot price a cart that has no tickets in it, and you cannot start a payment before you know the price. Here is the full sequence.

  1. Buyer opens the registration link

    GET /api/events/{eventUniqueId}/register/bootstrap

    One small, fast call. Answers: can they register at all, which tabs exist, what colour is the brand, which currency. Everything else waits.

  2. Buyer picks tickets

    GET …/register/sessions, then POST /api/events/cart, then POST /api/events/cart/{id}/lines

    Create the cart on the first ticket chosen, not on page load. Adding a line reserves real stock, and the countdown timer starts right here.

  3. Buyer types their details

    GET …/register/attendee-info, then POST …/lines/{lineId}/attendees

    Only for sessions that ask for attendee names. Whatever email you put on an attendee decides who gets that ticket by email.

  4. Buyer answers extra questions

    GET …/register/questionnaire, then POST …/cart/{cartId}/answers

    Only when the event actually asks for custom forms or questions.

  5. Show the price

    POST /api/events/cart/{id}/price

    Returns a separate total for each payment method, because fees differ. This is also where a discount coupon is accepted or rejected.

  6. Buyer pays

    GET /api/public/stripe/{paymentAccountUniqueId}/credentials, then POST …/checkout/intent, then Stripe.js

    Card fields appear on screen before the payment exists, so the Stripe key comes from its own call.

  7. Buyer lands on their order page

    POST …/checkout/confirm, then GET /api/events/orders/{orderUniqueId}

    The cart is finished and gone. From here the buyer has one permanent id: the order id.

  8. Emails go out

    Nothing for you to call — see section 10.

    Two different emails, to different people, for different reasons. The frontend sends neither.

The one rule you must never break: card numbers, CVC codes and bank account numbers go from the buyer's browser straight to Stripe. They never pass through our API, in any form, for any reason. Stripe's own components collect them. Our server only ever learns a PaymentIntent id. If a design ever asks you to POST a card number to our backend, that design is wrong — raise it, do not build it.

5. Page-loading calls

There are seven of these, and here is the thing that confuses people first: all seven return the exact same shape. The difference is which parts are filled in. The bootstrap call fills in the event details and leaves sessions empty; the sessions call fills in sessions and leaves most event details out.

Why? So one parser handles all seven, and so each screen downloads only what it needs. Loading every question for every session when the buyer only wants to read the description would be slow and wasteful.
GET /api/events/{eventUniqueId}/register/bootstrap No login needed

What is it for?

It sets up the page. It answers the questions you must have answers to before you can draw anything: is this event even open for registration, what tabs should appear, what colour is the brand, which currency, and does this event accept discount coupons.

This is the very first call the page makes. Everything else waits for it.

What do you send?

Nothing. No body, no query string. Just the event id in the URL.

How do you call it?

// The API function already exists — use it, do not write a new one
import { fetchEventRegistrationBootstrap } from "@/api/events"

export function useEventRegistration(eventUniqueId: string) {
  return useQuery({
    queryKey: ["event-registration", eventUniqueId, "bootstrap"],
    queryFn: () => fetchEventRegistrationBootstrap(eventUniqueId),
  })
}

GET /api/events/{eventUniqueId}/register/sessions No login needed

What is it for?

Everything that is actually for sale: each session, each ticket type inside it, how many are left, and which price is currently in force. This is the data the ticket picker draws.

availableForSale is a live number that changes as other people buy. Refetch when the buyer comes back to this tab, rather than trusting a copy from ten minutes ago — otherwise they will pick a ticket that is already gone and get a confusing error later.

Putting tickets in a cart does not reserve them. A cart is an intention; seats only leave inventory when the buyer starts paying. So one buyer sitting on the ticket picker with everything in their basket does not report the event sold out to anybody else, and availableForSale can fall while a buyer is still filling in the form. The order is measured against what is left at POST .../checkout/intent, and that call is where a buyer learns something sold from under them.
nextSeatsAvailableAtUtc is only sent when a ticket type has nothing left to sell, and it answers the question the buyer would otherwise have no way to ask: when do the seats come back? It is the moment the earliest hold another buyer is sitting on runs out. It is absent when the seats are committed to a payment and are not coming back.

Treat it as approximate. The housekeeping pass that actually returns the seats runs on its own minute-long cycle, so they reappear at or shortly after that time, never before it — poll rather than trusting the clock to be exact.

What is a "price period"?

Organizers often sell the same ticket cheaper early on — an early-bird price. Each ticket type therefore carries a list of price periods, each with its own dates. Exactly one of them has currentStatus: "Active", and that one's amount is today's price.

fullPrice is the normal, undiscounted price. When the active period is cheaper than fullPrice, show fullPrice struck through next to the real price — buyers respond to seeing the saving.

None of these numbers is a promise. They say what is available right now, and the only binding answer comes from starting payment.

controlTypePicks the widget: select, multiselect, file, text, and so on. multiselect is a checkbox group, not a dropdown, and its answer is comma-joined. Anything you do not recognise renders as a text input — never as nothing.

6. Cart calls

Read this before writing any cart code. The cart is not a list in React state. It is a real record on the server, it holds real stock away from other buyers, and it expires. Every cart call returns the whole updated cart, so you never have to work out the new state yourself — just replace what you had with what came back.
Think of a cart like a supermarket trolley that the shop is watching. Putting something in takes it off the shelf, so nobody else can buy it. If you wander off for twenty minutes, staff put it all back. That is exactly how this works.

7. Payment calls

How Stripe payments work here, in plain terms

Stripe gives you ready-made card input components. Those components must appear on screen before you know whether the buyer will actually press pay — so the payment record is created late, only when they submit. Stripe calls this the "deferred intent" flow.

Because the fields appear first, you need Stripe's public key before any payment exists. That is why there is a separate call just for the key.

Card payment — the exact steps
  1. Fetch the Stripe key: GET /api/public/stripe/{paymentAccountUniqueId}/credentials
  2. Mount Stripe's <Elements> with the grandTotal and currency you got from pricing.
  3. Buyer presses pay ⇒ await elements.submit(). If it reports a validation problem, stop here.
  4. Create the payment: POST …/checkout/intent ⇒ you get clientSecret and invoiceUniqueId.
  5. Save invoiceUniqueId now, before the next step. Explained below — this one really matters.
  6. Hand off to Stripe: stripe.confirmPayment({ elements, clientSecret, confirmParams: { return_url }, redirect: "if_required" })
  7. If it finishes without redirecting (normal for cards) ⇒ call POST …/checkout/confirm, then go to the order page.
  8. If it redirects (normal for bank transfers) ⇒ Stripe sends the buyer to your return_url, which is the order page. That page does step 7 itself.
Why step 5 matters. Once confirmPayment runs, the buyer's money can leave their account. If their laptop dies at that exact moment and you did not save invoiceUniqueId first, they have paid and there is no way for them to get back to their order. Save it first. Every time.

What is it for?

Someone handed the organizer a paper cheque. This records it and issues the tickets straight away, while the invoice stays marked as owing until the cheque clears.

This is the only call in this whole guide that needs a login. It creates tickets without any money having arrived. If it were public, anyone could mint themselves free tickets. Note that isOrganizerOnly on a payment method is only about what you display — this login requirement is the actual protection.

What do you send?

{
  "chequeReferenceNo": "CHQ-889210",
  "notes": "Collected at the front desk, 5 Aug."
}

chequeReferenceNo is required. A cheque has no Stripe transaction id, so this number is the only link between the deposit in the bank and the invoice it settles. Send it blank and the call is refused with "Cheque reference number is required." before any seat is claimed, so nothing is held for an order that cannot go through. It is not checked for uniqueness — two banks can legitimately print the same cheque number. notes stays optional.

What comes back (inside data)

{
  "cartUniqueId": "5c1d8e2f-6b7a-4c39-9d80-1e2f3a4b5c6d",
  "invoiceUniqueId": "9b0e7d61-4c2a-4f18-8e73-3d5b6a9c0e42",
  "invoiceNo": "EV-2026-004183",
  "amountDue": 470.61,
  "ticketCodes": ["GPS26-4X7K-2210", "GPS26-9M2B-2211"]
}

amountDue is what is still owed. It is not zero — that is the whole point of the cheque flow.

What you must do with it

  • Do not send a cheque to …/checkout/intent. That route only starts Stripe payments, and it refuses this one with "Cheque payments are recorded through the cheque endpoint." Branch on the selected method before the call, not on the refusal after it.
  • There is no Stripe step and nothing to confirm. This one call records the payment and issues the tickets. Do not mount the Payment Element, and do not call …/checkout/confirm afterwards.
  • Send the organizer to the order page using invoiceUniqueId. The cart id dies with the cart, so that is the only handle that survives.
  • Show amountDue. The tickets exist but the money has not arrived, so a confirmation that reads as fully paid is wrong.

When the seat is gone by the time you pay

Seats leave inventory when payment starts, not when they were picked, so this call is the first moment the order is measured against what is actually left. The first three answers come back from both …/checkout/intent and …/checkout/confirm; the last three only from …/checkout/intent, which is the only call that reaches the payment processor. All of them arrive as success: false with the sentence in message — never as a 5xx, so do not branch on the status code.

MessageWhat happened, and what to do
"'X' sold out while you were checking out and has been removed from your order. Review your order and try again." The order was changed under the buyer, so it was not charged. Re-price the cart and show them the new total before letting them pay again. If the tail reads "There is nothing left to pay for." instead, the whole order is gone — send them back to the ticket picker.
"'X' sold out before your payment could be taken. Your order was not charged." The buyer lost a rush for the last seats. Nothing on the order can still be bought. Treat it exactly like the sold-out case above — do not offer a retry.
"Someone else is booking these tickets right now. Please try again." Only ever returned while seats genuinely remain. A retry can succeed, so offer one. Back off briefly first rather than re-firing immediately.
"Payments are busy right now. Please wait a moment and try again." The payment processor throttled us, which happens when a rush of buyers all start payment in the same second. The buyer's seats are claimed and stay held for the rest of the purchase window, so a retry is the right offer — wait a few seconds before firing it. Do not send the buyer back to the ticket picker; they would lose a seat they already hold.
Any sentence about the card itself, e.g. "Your card was declined." Written by the payment processor for the cardholder to read, so show it as-is. The seats stay held, so let them try a different card without rebuilding the order.
"Payment could not be started. Please try again." Every other payment failure collapses to this one sentence on purpose — the underlying reason carries account and request identifiers that are not the buyer's to see. Offer a retry; if it repeats, send them to support with the order reference rather than looping.
Retrying on the two sold-out messages. They are final: the stock the buyer wanted is gone, and a retry loop only spends their patience. Every other message here can succeed on a second attempt, and the server decides which one you get by re-reading availability and by what the payment processor answered — never by guessing from the HTTP status.

8. The order status call

GET /api/events/orders/{orderUniqueId} No login · rate limited

What is it for?

This builds the confirmation page. It is the only call that still works after the cart is gone, and the only page a buyer can safely bookmark, refresh, or be sent back to.

orderUniqueId is the invoiceUniqueId you saved earlier.

Anyone with the link can see this page. There is no login. The id is long and random, which is what keeps it private. That is also why the buyer's email arrives already masked — p*********@example.com. Never display a full email address on this page from any other source.

Rate limit

The money breakdown

Everything needed to print a receipt is here, so the confirmation page never has to reach for the organizer-only invoice endpoint. charges is already ordered for display and contains only what the buyer was billed — a revenue-plan fee the organizer absorbs out of their own payout is deliberately absent, which is why the rows always add up to totalAmount.

  • taxAmount, platformCharges and serviceCharges are the bucket totals of charges. Each is null when nothing landed in it — drop the row rather than printing a zero.
  • amountPaid counts settled payments only; a failed attempt is not money received.
  • balanceAmount is null once nothing is owed, so a settled order renders no balance row.
  • lineItems carries no attendee contact details. The link is the only credential this page has.

Three states — this is the field you build the page around

Ignore invoiceStatus for display. Use orderState, which is deliberately simple: a buyer deserves one of three clear answers, not an eight-way accounting term.

StateMeansWhat to show
Confirmed Paid, tickets are theirs. Success message, list of tickets, "sent to p*****@example.com", venue with map link. Stop polling.

Failed Finished without tickets — cancelled, failed, or refunded. A clear explanation and a way to contact support, quoting invoiceNo. Stop polling. Never offer a "try again" button here — you do not know whether they were charged.

How to poll, exactly

pollAfterSeconds is the server telling you how long to wait before asking again. 0 means stop — you are done. Any other number is a minimum: you may wait longer, never less.

The existing implementation slows down over time, which is the right pattern:

First 15 seconds3 seconds

45 – 90 seconds10 seconds

Why stop after three minutes? Because a spinner that never resolves feels broken. An honest "still processing — check again" with a button feels like a system that knows what it is doing. Bank payments genuinely take days; nobody is going to sit and watch.

Two things that surprise people

  • A 404 is final. Show the "order not found" card and stop. Do not retry.
  • Free orders reach Confirmed with no payment at all. Do not write code that assumes a payment record exists.

9.1.1 The "sales have not opened" countdown card

This is the screen a buyer sees when they arrive early. It is not the cart timer in §9.6 — different data, different purpose, and they never appear at the same time.

QuestionAnswer
What turns it on? bookingStartDate from the bootstrap call is present and still in the future compared to the browser clock. Both conditions, not one.
What if it is null? No countdown at all. A null booking start means "sales were always open". Fall straight through to the canRegister check.
How much of the page does it take? All of it. The countdown replaces the whole page — it is not a banner above the wizard. The wizard must not mount, no cart is created, and no cart or payment call is made while it is on screen.
What does it contain? Event banner (or a "Banner not available" placeholder), a "Registration opens soon" badge, organizer, venue, then four tiles — Days, Hours, Minutes, Seconds — plus the opening time written out in the buyer's own local time.

Do not let the "refetch at zero" run on every tick. Guard it with a flag that is set the first time the deadline passes, and reset only when the event id or the booking date itself changes. Without that guard you fire one bootstrap request per second, forever.
Do not read bookingStartDate as local time. Like every date in this API it is UTC. If it arrives without a Z or an offset on the end, append Z before parsing — otherwise the browser treats it as local and the countdown is wrong by your timezone offset.

9.8 The discount coupon control, in full

This control caused a real bug once, so it is worth going through slowly. It has three states, not two.

State 1 — the control is not there at all

Show nothing when both of these are true:

  • acceptsDiscountCoupons === false, and
  • no coupon is currently applied to the cart.

acceptsDiscountCoupons is false when the event has no coupon a buyer could possibly redeem — either discounts are switched off for the event, or every coupon on it is deactivated, or every coupon is fully used up.

Showing the coupon box anyway "just in case". This was the actual bug: buyers were offered a coupon field on an event where no code could ever work. They typed codes, got "Discount coupon not found." every time, and concluded the site was broken. If no code can succeed, do not ask for one.

State 2 — empty, waiting for a code

  • Heading: "Have a coupon?"
  • A text input and an "Apply" button joined into one rounded control.
  • The Apply button is disabled while the input is empty or only spaces, and shows a not-allowed cursor when disabled.
  • Once enabled it takes the brand colour; while disabled it is grey.
  • Pressing Enter in the input applies the code — buyers expect this and it costs one line.
  • The code is trimmed before sending. A trailing space must not cause a rejection.
  • While the request is in flight the button shows loading with the text "Applying...".
  • The whole control is full width on mobile, capped around 420px from tablet up.

State 3 — a coupon is applied

The input disappears and is replaced by a summary row:

  • The code shown as a green badge — SUMMIT10.
  • The amount saved beside it — -$49.80 applied — but only when the discount is greater than zero. A "-$0.00 applied" label is noise.
  • A "Remove" button with an × icon, disabled while any cart request is in flight.
  • The row is outlined in the event's brand colour, so it reads as an active, successful state.
The important exception. When a coupon is applied, keep the control visible even if acceptsDiscountCoupons is false. That combination happens in real life — the organizer deactivates the coupon while a buyer already has it on their cart. Hide the control then and the buyer is stuck with a discount they can see but cannot remove.

Where does a rejection message appear?

Not inside this card. A rejected coupon fails like any other cart request, and it surfaces through the cart's shared error banner — the same place a sold-out ticket or an expired cart reports itself. One error location, not five.

This is a deliberate design choice, and a good habit generally: one shared place for a whole feature's errors beats a bespoke error slot inside every component. Buyers learn where to look, and you write the handling once.

Applying and removing both go through the same call

There is no "remove coupon" endpoint. Both actions call Price the cart:

  • Apply: { "couponCode": "SUMMIT10" }
  • Remove: { "couponCode": null }

9.10.1 What happens after a successful registration

A settled order is the end of the buyer's journey, so the page asks them what they want next instead of leaving them parked on a screen whose cart is already spent.

Priya is both the buyer and an attendee, so she gets one ticket email, not two. The system merges her into a single recipient and gives her the buyer version.

10.2 When each email is triggered

What happenedConfirmation?Tickets?Why
Payment settled, everything ticketed Yes Yes The normal, happy path.
Payment settled but a line got no tickets Held back Yes The order may still end up refunded. Telling someone "you're confirmed!" and then refunding them is worse than a short delay. It gets sent once the order is whole.
Money arrived but the invoice did not reach Paid No No The order goes into a recovery process instead.
Your confirm fast-path call Yes Yes Both jobs are safe to trigger twice, so the webhook and this call can both do it.
Payment failed No No Reserved stock is released. There is nothing to confirm.

Organizer pressed "resend" No Yes Resending the thank-you would read like a second purchase.

10.3 When emails do not go out at all

SituationWhat happens
Buyer's email is missing or invalidNo confirmation. Logged as a warning.
Digital tickets switched off for every sessionNo ticket email at all — the organizer scans people in at the door instead. This is why a Confirmed order can legitimately show no tickets.
Digital tickets off for some sessionsOnly the enabled sessions' tickets get sent.
One recipient's email bouncesOnly that one fails. Everyone else still gets theirs, and it is retried.
QR code generation failsThe PDF is still sent — the ticket code is printed as text too.
Already sentSkipped. Both jobs remember what they already sent, so nobody gets duplicates.

10.4 What this means for your copy

  • Do not write "we have sent your tickets". Write "your tickets are on their way to p*****@example.com". You genuinely do not know whether the email has landed yet.
  • There is no way for a buyer to check email delivery status. Do not build UI that implies there is.
  • A Confirmed order with an empty ticket list is normal. Handle it without an error state.

11. When things go wrong

11.1 How to show an error

  • Show message from the envelope. It is already written for buyers.
  • Never show error.message from axios. It leaks technical detail and means nothing to a buyer.
  • Use the shared extractApiError helper — it handles this for you.
  • validationErrors maps field names to messages. Show each one under its own input.
The server deliberately never sends stack traces, internal ids or framework details to the browser. If you ever see one, that is a backend bug worth reporting — it is a small security leak.

11.2 Situations your UI must handle

SituationWhat to do
Cart expires while they are typingBlocking dialog, clear the saved cart id, back to ticket selection. Never let them reach the pay button on a dead cart.
Tickets sell out between choosing and addingYou get a 400. Show the message and refetch sessions so the counts update.
Browser closes during paymentThe saved invoiceUniqueId gets them back to their order on the next visit. This is exactly why you save it first.
They come back from a bank redirectThe order page handles it. Same page, same code.
Confirm call fails after a successful paymentDo not say the payment failed. Go to the order page and let polling resolve it. Stripe's webhook is the real authority.
Coupon runs out between pricing and paymentHandled on the server; the order settles at the price you were quoted. Nothing for you to do.
Order polling returns 429Slow down. Never poll faster than pollAfterSeconds.
A ticket is switched off while it sits in the cartPricing and cart fetch will reflect it. Surface any change before the pay button, not after.

11.3 Security rules you must not break

RuleWhy
Card and bank details go browser → Stripe onlyThey must never touch our API. Stripe's own components collect them, and Stripe carries the compliance burden.
No localStorage or sessionStorage, for anythingProject-wide rule. Use short-lived, path-scoped cookies. Helpers already exist.
Organizer-only flags are display onlyThe server checks permissions on its own. A client-side check protects nothing — it just tidies the UI.
Sanitise organizer HTML before renderingDescription, terms and refund policy are typed by other people. Unsanitised, they are a script-injection route into your buyers' browsers.
Show coupon errors word for wordMaking them more specific turns a public page into a coupon-guessing tool.
Validate every response with ZodIf the server sends an unexpected shape, throw at the boundary rather than letting bad data flow into components and crash somewhere confusing.

12. Final checklist before you call it done

Go through this honestly. If a box is unchecked, the work is not finished.

Data and calls

  • ☐ Every server call goes through a file in src/api/ — no axios in a component.
  • ☐ Every response is unwrapped from the envelope and validated with Zod.
  • ☐ Every query handles all three states: loading, error, and data.
  • ☐ Every loading state shows a skeleton, not a spinner and not a blank area.
  • ☐ Every mutation handles both onSuccess and onError.
  • ☐ No URL is hardcoded — all come from API_ROUTES.

Money

  • ☐ No total is calculated in JavaScript. grandTotal comes from the server.
  • ☐ The pay button states the exact amount.
  • ☐ Amounts are formatted with Intl.NumberFormat.
  • ☐ The buyer cannot press pay while prices are being refetched.

Payment safety

  • ☐ invoiceUniqueId is saved before confirmPayment is called.
  • ☐ return_url points at the order page, not the cart.
  • ☐ A failing confirm call does not tell the buyer their payment failed.
  • ☐ The countdown timer is removed the moment payment succeeds.
  • ☐ No card or bank detail is ever sent to our API.

Responsive and accessible

  • ☐ Checked at 320, 375, 768, 1024, 1440 and 1920 pixels.
  • ☐ The page never scrolls sideways at any width.
  • ☐ Tables scroll inside their own container.
  • ☐ Modals are full screen on mobile.
  • ☐ Tap targets are at least 44 × 44 pixels.
  • ☐ Every input has a real label; focus outlines are visible.
  • ☐ Pointer cursor on clickable things; not-allowed on disabled things.

Tests

  • ☐ Tests are in the same change as the code, not "coming later".
  • ☐ Each test name says which rule it protects.
  • ☐ Failure paths are tested as thoroughly as success paths.
  • ☐ npm run lint and npm run build are clean.
